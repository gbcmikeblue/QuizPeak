# 05 · 技术选型与架构方案

> 依据需求方决策：**admin 用推荐后台二次开发（Node/Next.js 优先）、H5 + 小程序用 uni-app、支付按中国国内方案、三端功能一致、后台只做一套。**

## 1. 总体结论（TL;DR）

| 端 | 选型 | 说明 |
| --- | --- | --- |
| `admin/` 运营后台 | **Next.js 15 (App Router) + TypeScript + Tailwind + shadcn/ui**，基于开源模板 `shadcn-admin` 二次开发 | 纯前端 + 直接调 API 服务；服务端渲染无强需求，但表格/表单生态成熟、开箱即用 |
| `server/` 服务端 API | **NestJS 10 (Node 20) + Prisma + PostgreSQL 16 + Redis 7 + BullMQ** | 四端共用一套 REST API；定时任务（开赛/结算/发奖/订单超时）在同一进程内以 Worker 承载 |
| `web-pc/` 用户端 | **Next.js 15 + Tailwind**（SSR/SSG 用于文章、竞赛、Quiz 详情页 SEO） | 与后台同技术栈，组件与类型可复用 |
| `web-h5/` + `miniprogram/` | **uni-app（Vue 3 + TypeScript + Vite）**，一套代码编译到 H5 与 `mp-weixin` | H5 与小程序共享 90% 业务代码，仅支付与登录做条件编译 |
| 存储 | 阿里云 OSS / 腾讯云 COS + CDN | 图片（封面、头像、文章配图）直传，后端只存 key |
| 部署 | Docker Compose（web ×3、server、pg、redis、nginx）+ 云服务器 | 后续可平滑上 K8s |

**为什么不选 Python（Django）**：本项目 90% 的业务是 CRUD + 定时任务 + 支付回调，Node 全栈可以让 `admin` / `web-pc` / `server` 共用 TypeScript 类型定义与校验 schema（zod），三处代码不重复；若团队更熟 Python，可用 **Django + DRF + Django Admin** 平替 `server/`，其余端方案不变（见第 12 节对比）。

### 4.2 关键业务规则实现位置

| 规则 | 实现 |
| --- | --- |
| 单题 120s | 服务端为每个 Attempt 生成 `question_started_at`，提交时校验 `now - started_at ≤ 120s`，超出判错；前端倒计时仅展示 |
| 扣费报名 | `prisma.$transaction`：校验余额 → 扣 `user.coin` → 插 `coin_transaction` → 插 `enrollment`（唯一索引 user+quiz/contest） |
| 关卡解锁 | 提交成绩时计算正确率，`≥ unlock_threshold` 则 upsert `level_progress.unlocked` |
| 竞赛排名 | 交卷写 `contest_attempt(score, total_time)`；Redis ZSet 实时榜 + 定时落库；结束任务读取全量排序结算 |
| 发奖幂等 | `contest_reward(contest_id, user_id, rank)` 唯一索引 + 任务状态机 |
| 金币一致性 | 所有变动只能通过 `wallet.service.change()`，禁止直接 update，函数内写流水与余额快照 |
| 防刷 | Redis 限流（滑块/验证码）、邀请去重表（`invite_log.device_id` + `phone_hash`） |

## 5. 用户端（`web-pc/`）

- Next.js 15 App Router：`(marketing)` 组做 SSR/SSG（首页、文章、About、Contact、Quiz/Contest 详情），个人中心与答题页用客户端渲染（`"use client"`，因为强交互）。
- SEO：文章与竞赛/Quiz 详情输出 `generateMetadata`，多语言 `hreflang`，`sitemap.xml` + `robots.txt`。
- 答题页/答题弹窗与 H5 共用「答题引擎」逻辑（放到 `packages/shared`：计时、选项、判分展示）。
- 状态管理：TanStack Query（服务端状态）+ Zustand（UI 状态），不引入 Redux。
- 表单：react-hook-form + zod。
- 富文本渲染：`sanitize-html` 白名单（源站 `<p>` 外露问题的根治）。

### 6.1 工程约定

```

├─ src/pages/…           # 页面，与 PC 一一对应
│   ├─ index/index.vue           首页
│   ├─ quiz/list.vue  quiz/detail.vue  quiz/play.vue  quiz/result.vue
│   ├─ contest/list.vue  detail.vue  play.vue  leaderboard.vue
│   ├─ article/list.vue  detail.vue
│   ├─ user/profile|history|favorites|badges|leaderboard|invite|settings.vue
│   ├─ wallet/index|buy|withdraw|coin-history.vue
│   ├─ ticket/list|create|detail.vue
│   ├─ auth/login|register|forgot.vue
│   └─ game/wordling|hexling.vue
├─ src/api/              # 请求封装（uni.request 拦截器）
├─ src/store/            # pinia
├─ src/i18n/             # vue-i18n，复用 packages/i18n
└─ src/components/       # 卡片、Tab、空态、倒计时环
```

- **条件编译**：`// #ifdef MP-WEIXIN` 处理小程序登录/支付/分享；`// #ifdef H5` 处理 H5 支付跳转与 `history` 路由。
- **移动端布局**：底部 Tab（首页 / 竞赛 / 文章 / 我的）；列表单列；答题页选项大按钮（≥44px 高）、底部固定操作栏。
- **登录**：H5 = 手机号验证码 / 微信网页授权；小程序 = `wx.login` + `openid` + 手机号快捷授权。
- **支付**：H5 = 微信 H5 支付（`redirect_url` 回跳）/ 支付宝 WAP；小程序 = `uni.requestPayment`（微信 JSAPI）。
- **小程序分包**：主包放首页/竞赛/我的，`game`、`article` 放分包，控制 2MB 主包体积。
- **分享**：小程序 `onShareAppMessage`；H5 用微信 JS-SDK 或复制链接兜底。

### 6.2 与 PC 的一致性

- 功能范围一致（需求方确认），但交互适配：PC 的三 Tab 详情 → 移动端吸顶 Tab；侧边栏 12 项 → 「我的」页九宫格 + 二级页。
- 一套 UI 变量（主色/圆角/间距）在 `packages/ui/tokens.json` 中共享给 Tailwind 与 uni-app SCSS。

### 7.0 现行方案（摘要）

| 项 | 方案 |
| --- | --- |
| 积分来源 | 签到（每日 1 次）、看广告（每日 5 次）、给上榜选手点赞（每日 5 次）、活动 |
| 看广告 | 接入激励视频 SDK（腾讯优量汇 / 穿山甲）：客户端播放完成 → 上报 `transId` → 服务端验签 + 唯一性校验 → 发积分 |
| 发放服务 | `PointsService.applyChange(tx)`：条件更新余额 + 写流水 + 余额快照，`(type, refType, refId)` 唯一保证幂等 |
| 风控 | 每日次数上限（`AdView`、`PointLike` 计数）、点赞同一人每日一次、单用户积分增速告警 |
| 数据库 | `PointTransaction` / `DailyCheckin` / `AdView` / `PointLike` / `Activity` / `ActivityReward` |
| 合规 | 无充值、无提现、无现金等价物；积分不可转让、不可兑现；协议中声明平台可依规调整 |

### 7.1（历史）充值设计 —— 已作废

### 7.1 充值（Buy Coins）

| 渠道 | PC | H5 | 小程序 |
| --- | --- | --- | --- |
| 微信支付 v3 | Native 扫码（`/v3/pay/transactions/native`） | H5 支付（`/h5`） | JSAPI（`/jsapi`） |
| 支付宝 | 电脑网站支付 `alipay.trade.page.pay` | 手机网站支付 `alipay.trade.wap.pay` | 小程序内调起（需支付宝小程序或用 H5 兜底） |

- 套餐（默认，可在后台改）：`6 元 = 60 金币`、`30 元 = 315 金币`（+5%）、`68 元 = 734 金币`（+8%）、`128 元 = 1434 金币`（+12%）、`328 元 = 3772 金币`（+15%）。
- 订单状态机：`待支付 → 已支付 / 已关闭 / 已退款`；30 分钟未支付自动关单（BullMQ 延时任务）。
- 回调处理：验签（微信平台证书 / 支付宝公钥）→ 查单二次校验 → 事务加币 → 幂等（`out_trade_no` 唯一 + 状态机）→ 返回成功。
- 对账：每日定时拉取账单，差异单进后台「对账异常」列表。
- 退款：后台发起退款（支持全额/部分），成功后扣回金币（不足则记负数余额）。

| --- | --- | --- |
| 微信零钱 | 微信支付「商家转账到零钱」 | 需用户先完成微信授权拿到 openid；单笔限额按商户配置 |
| 支付宝 | 支付宝「单笔转账」 | 需姓名 + 支付宝账号 |
| 银行卡 | 财务线下打款 + 后台回填流水号 | 无自动通道，作为兜底 |

- 规则：最低 10 元、手续费 2%（最低 1 元）、T+1 到账、单日限额后台可配、每人每日最多 1 单。
- 流程：申请（冻结金币）→ 待审核 → 通过（调通道打款）→ 已完成；驳回 → 解冻退币。
- 审计：每单记录操作人、时间、请求/响应报文（脱敏）。

### 7.3 合规要点（必须提前处理）

1. **ICP 备案 + 公安备案**，小程序需主体认证；含支付功能建议具备 ICP 许可证（经营性）。
2. **虚拟货币风险**：金币不得兑换法定货币形成「双向兑换」类赌博/资金池风险 —— 本项目「充值得金币 + 金币可提现」属于双向兑换，需法务评估；**建议方案：金币仅站内消费，提现通道只对「竞赛奖金」开放且设上限/实名要求**（当前需求含提现，落地前必须确认）。
3. **抽奖/竞赛合规**：竞赛有报名费 + 奖金，需避免构成博彩；须公示规则、限制未成年人参与（实名 + 年龄校验）。
4. **支付资质**：微信支付/支付宝商户号需与备案主体一致。
5. **个人信息**：手机号、身份证（如提现）需加密存储与最小化采集，提供注销入口。

## 8. 登录鉴权与安全

- 认证：手机号 + 短信验证码为主；邮箱密码为备；微信扫码/公众号授权作为快捷登录。
- Token：`accessToken`（30min，JWT）+ `refreshToken`（7d，HttpOnly Cookie / 小程序 storage），支持多端同时在线。
- 密码：`argon2id` 哈希；后台账号强密码 + 图形验证码 + 可选 2FA（对应设置的 2FA 开关）。
- 接口安全：全局限流（Redis 令牌桶）、敏感接口二次校验（提现、改密）、参数 zod 校验、SQL 注入由 Prisma 规避、XSS 由富文本白名单规避。
- 答题安全：题目接口不返回 `answer`；选项乱序种子按 attempt 存储；服务端计时；提交频率限制。
- 日志：操作审计（后台）、登录日志、支付日志；Sentry 采集前端与 Node 异常。

### 10.1 开发与构建提速（2026-10-23 实测）

日常迭代**不要用生产构建**。生产构建只在发版前跑一次。

#### 实测数据（本机 Windows 11，Node 22）

| 操作 | 耗时 | 说明 |
| --- | --- | --- |
| `next build`（web-pc 全量） | **43.8s** | 每次改代码都跑就太慢 |
| `next dev` 首次访问某路由 | 2.3s | 按需编译该路由 |
| `next dev` 再次访问 | **0.19s** | 命中缓存 |
| 改代码后 HMR | **<1s** | 无需重启进程 |
| `nest build`（全量） | 4.2s | 含 CLI 启动开销 |
| `nest start --watch` 热重启 | ~1.5s | 改完自动重编译 + 重启 |
| 改后端 + 改前端各验证一次（旧方式） | **≈65s** | build + 杀进程 + 固定等待 |
| 同上（新方式） | **≈3s** | watch/HMR + 轮询探活 |

#### 日常命令

```bash
npm run db:local      # 终端 1：本地数据库（常驻）
npm run dev:all       # 终端 2：api(watch) + web(dev) + admin(dev) 一次起好
npm run verify        # 任意终端：200ms 内检查四个服务与关键接口
```

- `dev:all` 支持 `-- --no-admin` 只起 api + web；日志带 `[api] / [web] / [admin]` 彩色前缀；Ctrl+C 一起停
- 只有准备提交/发布时才执行：
  ```bash
  npm run build -w @quizpeak/server && npm run build -w @quizpeak/admin && npm run build -w @quizpeak/web-pc
  ```

#### 构建产物的生成与清理（避免大量文件反复增删）

| 策略 | 做法 |
| --- | --- |
| 服务端不再每次清空产物 | `server/nest-cli.json` 关闭 `deleteOutDir`（原来每次 build 删除 `dist/` 下 140+ 个文件）；改为覆盖式编译，配合 `tsconfig` 的 `incremental` 与 `.cache/ts-server.tsbuildinfo` |
| 前端用 dev 编译 | `next dev` 在 `.next` 内做增量，**不重建整个目录**；生产构建才整体重建 |
| 一次性清理用 Node 删除 | `npm run clean`（`scripts/clean.mjs`）用 `fs.rm` **直接删除、不进回收站**，比资源管理器删除快很多；`npm run clean -- --all` 额外清理 `.next/cache` |
| 缓存目录不入库 | `.cache/` 已加入 `.gitignore` |

> 关于「删除的文件进了回收站」：`next` 与 `tsc` 内部的删除都走 `fs.rm`，本质是永久删除，不会进回收站。若在回收站看到大量 `.next` / `dist` 文件，通常是**手动用资源管理器删除**或第三方清理工具（如某些“磁盘清理/文件历史”软件）代为删除所致。统一改用 `npm run clean` 即可避免。

#### 常见坑

1. **不要并行构建同一端**：两个 `next build` 同时写同一个 `.next` 会互相破坏（本项目曾出现构建失败、`next start` 报缺文件）。构建一律串行，或前端在后端构建期间保持 `next dev` 运行。
2. **`next start` 与 `next dev` 不能共用端口**：切换模式前先停旧进程（`npm run verify` 可确认端口占用情况）。
3. **`prisma generate` 不必每次跑**：只有 `schema.prisma` 变更后才需要。
4. **可选加速**：把 `node_modules`、`.next`、`.cache` 加入 Windows Defender 排除列表，构建通常再快 10~20%（需管理员权限，自行操作）。
5. **`incremental` 对 server 收益有限**（实测 4.2s → 3.8s，主要耗时在 CLI 启动），真正价值是**不再每次删除 dist**；若遇到“改了文件名但旧产物仍在”的怪问题，执行一次 `npm run clean` 即可。
